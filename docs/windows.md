# VOICEog на Windows: как это живёт

Этот файл — для человека. Объясняет, что происходит на Windows и почему сделано
именно так. Упаковочные детали построчно тут не повторяются — они в
[docs/packaging.md](packaging.md) и
[window/packaging/windows/README.md](../window/packaging/windows/README.md).
Здесь — общая картина и то, обо что спотыкаются на живой машине.

---

## 1. Суть: что где крутится

На Windows работают **два процесса**, и это важно понять, чтобы не искать багу не
там, где она есть:

- **окно** `voiceog-window.exe` — тонкая рамка (Rust: tao + wry + tray). Оно
  ничего не распознаёт, а показывает морду.
- **сервер** `node.exe server\src\server.mjs` — «ядро»: распознавание речи, запись
  микрофона, глобальный хоткей, вставка текста. Прицеп рядом с окном, отсюда
  название **sidecar**.

Морду в окне рисует **WebView2** — это системный движок Edge/Chromium, а **не наш**.
Свой браузер внутрь не тащим: так же, как на Linux окно берёт системный
`webkit2gtk`. Отсюда простое следствие: если на машине нет WebView2, окну нечем
рисовать (что делать — ниже, в разделе 2).

Ядро (распознавание, страница, HTTP-API) кроссплатформенное. Системная обвязка
вынесена в `src/platform/`, и на Windows подставляется свой набор адаптеров —
Linux-путь не тронут. Выбор происходит один раз по `process.platform`:

| Точка входа | Windows-адаптер | Чем внутри |
|---|---|---|
| запись микрофона (хоткей/фон) | `src/platform/win/recorder.mjs` | `ffmpeg` (`-f dshow`) |
| вставка текста | `src/platform/win/inject.mjs` | `Set-Clipboard` + `SendInput` |
| глобальный хоткей | `src/platform/win/hotkey.mjs` | `uiohook-napi` |
| запасной хоткей ОС | её **нет** | uiohook сам держит глобальную клавиатуру |

Часть зависимостей сервера — не JS, а **готовые бинарники под конкретную ОС**.
Именно поэтому win-`node_modules` нельзя взять из Linux-сборки: в них лежат
`linux-ELF`, а не `PE`-файлы под Windows. Что чем является:

| Пакет | Что даёт | Почему per-OS |
|---|---|---|
| `sherpa-onnx-node` + `sherpa-onnx-win-x64` | распознавание Parakeet | `sherpa-onnx.node` + `onnxruntime.dll` собраны под платформу |
| `uiohook-napi` | глобальный хоткей | префабр `prebuilds/win32-x64/uiohook-napi.node` |
| `ffmpeg-static` | запись микрофона (dshow) | `ffmpeg.exe` вместо линуксового `ffmpeg` |

> Путей ввода два. **Кнопкой в морде** звук берёт само окно (WebView2, Web Audio)
> и шлёт PCM на `/transcribe`. **По хоткею** запись в фоне делает сервер через
> `ffmpeg -f dshow` — окно в этот момент может быть не в фокусе. Обоим нужен один
> формат: **PCM 16 кГц моно 16-бит**. `ffmpeg.exe` берёт его с любого
> DirectShow-устройства и едет в комплекте — отдельно качать не надо.

Свежие npm (11+) по умолчанию блокируют install-скрипты пакетов. Без них
`uiohook-napi` и `ffmpeg-static` не поставят свои бинарники. Лечится один раз:

```bat
npm rebuild uiohook-napi ffmpeg-static
```

Сколько у нас `node.exe`: портативный **v22.23.3** (LTS «Jod»), его скачивает
`sidecar/provision.sh` и сверяет sha256. Отдельно ставить Node на машину юзера не
нужно — он уже внутри установщика.

## 2. Что нужно на машине

| Что | Зачем | Как быть |
|---|---|---|
| Windows 10/11 | целевая ОС; окно — x64 | — |
| WebView2 (Evergreen) | им окно рисует морду | на Win11 обычно уже стоит; установщик проверяет реестр и умеет запустить bootstrapper |
| микрофон | запись речи | любой, видимый в системе; VOICEog сам выберет тот, где есть звук |
| PowerShell | вставка текста и буфер | есть в любой Windows, ставить не надо |

**Про WebView2.** В установщик вшит **загрузчик** (bootstrapper) — сам движок он
не тащит, а ставит из системы/интернета. Установщик смотрит реестр в трёх местах;
не нашёл — запускает Evergreen Bootstrapper. Если положить рядом с проектом
`MicrosoftEdgeWebview2Setup.exe`, он попадёт внутрь установщика; иначе установщик
предложит скачать вручную. Проверить руками, есть ли движок:

```powershell
Get-ItemProperty 'HKLM:\SOFTWARE\WOW6432Node\Microsoft\EdgeUpdate\Clients\{F3017226-FE2A-4295-8BDF-00C3A9A7E4C5}' | Select pv
```

**Про микрофон.** По умолчанию VOICEog **сам перебирает аудио-устройства** и берёт
то, где реальный сигнал — иначе легко нарваться на «мёртвый» микрофон и писать
тишину. Своё устройство задаётся в морде (блок **[4] Микрофон**) или переменной
`VOICEOG_AUDIO_DEVICE` (имя как в списке DirectShow). Там же кнопка **«Проверить
микрофон»** — пишет 1,5 с и показывает уровень и распознанный текст: сразу видно,
слышит он или нет. Свой `ffmpeg` — переменная `VOICEOG_FFMPEG`.

## 3. Сборка и установка (коротко)

Полная раскладка — в [docs/packaging.md](packaging.md). Суть: собрать надо окно и
sidecar (сервер), и **на разных машинах**.

| Шаг | Где собирать | Команда | Что выходит |
|---|---|---|---|
| окно (`voiceog-window.exe`) | Linux, кросс | `cargo xwin build --release --target x86_64-pc-windows-msvc` | `window/target/x86_64-pc-windows-msvc/release/voiceog-window.exe` |
| `node.exe` для sidecar | Linux | `window/packaging/windows/sidecar/provision.sh` | `window/target/win-sidecar/node.exe` |
| win-`node_modules` + сервер | **только Windows/CI** | `build-node-modules.ps1` | `window/target/win-sidecar/` |
| установщик | где есть `makensis` | `window/packaging/windows/build-installer.sh` | `window/target/VOICEog-setup.exe` |

Ключевое, что стоит запомнить: **win-`node_modules` собирается исключительно на
Windows или CI-раннере `windows-latest`**. Кросс-сборкой это не лечится:
`npm ci` тянет бинарники под ту ОС, на которой запущен, а MSVC-тулчейн и
`ffmpeg-static`-postinstall под Linux не отрабатывают.

В `exe` окна **статически прилинкован только `WebView2Loader`** — поэтому
отдельных DLL рядом не надо. А **bootstrapper** (`MicrosoftEdgeWebview2Setup.exe`) —
это отдельный файл: он попадает в установщик, только если лежит рядом с проектом
(`voiceog.nsi:100-102`).

**Что получает юзер:** один `VOICEog-setup.exe`, ставится **per-user, без прав
администратора** — в `%LOCALAPPDATA%\VOICEog`. Внутрь кладутся окно, `node.exe`,
сервер, win-модули и (опционально) модель. Запись для удаления — в
`HKCU\Software\Microsoft\Windows\CurrentVersion\Uninstall\VOICEog`.

Про модель: она ~641 МБ распакованной и в репу не входит. Если установщик собран
с `WITH_MODEL=0`, модель скачается при первом старте (~487 МБ, качает
`launch.vbs`).

## 4. Лончер: тихо или с логами

Ярлыки в Пуске и на Рабочем столе зовут не `exe` напрямую, а **`launch.vbs`** — так
окно консоли не мигает. `launch.vbs` по шагам:

1. Сервер уже отвечает на `http://127.0.0.1:7777/health`? Не трогает его — мог
   поднять автозапуск или сам пользователь.
2. Иначе **сначала добавляет** `server\node_modules\sherpa-onnx-win-x64` в `PATH` —
   оттуда sherpa грузит свои DLL.
3. Затем запускает `node.exe server\src\server.mjs` **скрытно** и ждёт до 60 с,
   пока сервер откликнется. Долго — потому что сервер грузит модель (сотни МБ).
4. Открывает `voiceog-window.exe` и ждёт, пока его закроют. Крестик **прячет окно
   в трей**; реальный выход — «Выход» в меню трея.
5. Окно закрыли — гасит **только свой** сервер (по `node.exe`, чья командная
   строка указывает на наш `server.mjs`). Чужой не трогает.

Если надо видеть логи — рядом лежит **`voiceog-console.cmd`**: то же самое, но с
видимой консолью, `Ctrl+C` в ней останавливает сервер. Это для отладки; обычный
запуск — ярлык с `launch.vbs`.

Автозапуск при входе (per-user, без админа):

```powershell
powershell -ExecutionPolicy Bypass -File scripts\install-autostart.ps1
# снять:
powershell -ExecutionPolicy Bypass -File scripts\install-autostart.ps1 -Remove
```

Ярлык `VOICEog.lnk` в папке «Автозагрузка» (per-user) зовёт `scripts\run-hidden.vbs`,
тот тихо запускает `voiceog.cmd` — окно консоли не мигает. Порт переопределяется
`VOICEOG_PORT`; `VOICEOG_URL` тут ни при чём — `voiceog.cmd` его не читает.

Важно: автозапуск поднимает **только сервер** — цепочка `install-autostart.ps1` →
`run-hidden.vbs` → `voiceog.cmd` → `node src\server.mjs`. Окно и трей при входе
**не** открываются: за мордой надо кликнуть ярлык руками. На Linux иначе — там
`install-window-autostart.sh` поднимает и окно.

## 5. Хоткей и вставка на Windows

Тут всё построено на двух вещах: **uiohook** ловит клавиатуру, а **буфер +
Ctrl+V** доставляет текст.

**Хоткей — `uiohook-napi`.** Он даёт и `keydown`, и `keyup`, поэтому режим *hold*
(держишь — говоришь — отпустил) работает так же, как `evdev` на Linux.
Модификаторы берутся из флагов самого события, а не считаются руками. Запасного
хоткея средствами ОС на Windows **нет и не нужно** — uiohook ловит глобально, в
любом приложении.

**Вставка — `Set-Clipboard` + `SendInput`.** Текст «по клавишам» не набирается
(раскладку кириллицы так не обойти), поэтому делаем как на Linux: кладём текст
в буфер и жмём Ctrl+V. Только средства другие:

- буфер — `Set-Clipboard` через PowerShell (честный Unicode для кириллицы);
- Ctrl+V — `keybd_event` (`SendInput`) на уровне системы, а не
  `WScript.Shell.SendKeys`. `SendKeys` из скрытого процесса ненадёжен (у него нет
  своего окна), а `keybd_event` бьёт по активному окну всегда.

Всё делается одним вызовом PowerShell, чтобы не дёргать его дважды.

**Про UIPI, честно.** Windows не даёт менее привилегированному процессу слать
нажатия в более привилегированное окно. Поэтому в окна, запущенные **от имени
администратора**, вставка не пройдёт. Правило простое: **запускай VOICEog тем же
уровнем прав, что и целевое окно**. И помни: текст идёт через буфер обмена —
текущее содержимое буфера перезапишется.

| Задача | Linux | Windows |
|---|---|---|
| запись микрофона | `pw-record` / `parec` / `arecord` / `ffmpeg` | `ffmpeg` (`-f dshow`), бинарь в комплекте |
| вставка в окно | `wl-copy` + `ydotool` / `dotool` / `wtype` / `xdotool` | `Set-Clipboard` + `SendInput` (`keybd_event`) |
| глобальный хоткей | `evdev` | `uiohook-napi` (`keydown`+`keyup`, режим *hold*) |
| запасной хоткей ОС | GNOME `gsettings` | не нужен |

Запуск и управление из консоли:

```bat
voiceog.cmd            :: старт сервера (поставит зависимости и модель)
voiceog.cmd toggle     :: старт/стоп записи (это же дёргает хоткей)
voiceog.cmd status     :: состояние
```

## 6. Ограничения (честно)

- **Только x64.** Всё собрано под `win32-x64`: `sherpa-onnx-win-x64`, префабр
  `uiohook-napi/prebuilds/win32-x64`, `node.exe` win-x64, кросс-цель
  `x86_64-pc-windows-msvc`. На ARM-окнах «из коробки» не поедет.
- **Нативные модули — только под win32.** На Linux их не собрать, `verify-
  sidecar.sh` там честно покажет `[нет]`. Собранные не на Windows нативники
  `.ps1` отсеет по PE-заголовку «MZ».
- **Вставка — через буфер.** Текущий буфер перезапишется.
- **UIPI.** В окна от админа не вставит — см. раздел 5.
- **WebView2 должен быть на машине.** Установщик умеет его доставить, но если и
  bootstrapper не сработал — окну нечем рисовать.
- **По-настоящему проверить можно только на живой Windows.** CI и Linux-машина
  показывают, что sidecar собран целиком (файлы на месте, нативники — валидные
  `PE`), но **GUI не покажут**: ни WebView2, ни микрофон, ни вставку, ни трей.
  Это проверяется руками на Windows.
