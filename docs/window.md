# Окно VOICEog: нативный пульт

Этот файл — для человека, а не для компилятора. Объясняет, зачем нужно окно,
как его собрать, запустить и поставить в автозапуск. И почему некоторые вещи
сделаны «вот так, а не иначе» — потому что иначе не работает.

---

## Зачем окно вообще нужно

Раньше морда VOICEog (та самая с кнопкой «НАЖМИ И ГОВОРИ») жила во **вкладке
браузера**. Это неудобно: вкладку можно случайно закрыть, её не видно среди
двадцати других, нет иконки в трее, и выглядит это как сайт, а не как программа.

Поэтому сделали **отдельное окно-программу**: `window/` (Rust). Важная деталь:
**морду никто не переписывал**. В окне живёт ровно тот же веб-интерфейс, который
отдаёт сервер VOICEog. Окно — это просто «рамка» вокруг него: с заголовком,
своим размером и иконкой в трее.

> Простая аналогия: раньше кино ты смотрел в браузере на сайте, теперь — в
> отдельном плеере. Фильм тот же, просто смотрится и запускается удобнее.

### Из чего оно собрано и почему

Окно — тонкая обёртка на трёх кирпичах:

| Кирпич | Что делает | Почему взяли |
|---|---|---|
| **tao** | создаёт окно, крутит цикл событий | лёгкий, не тащит за собой целый фреймворк |
| **wry** | рисует внутри окна системный браузерный движок | использует уже установленный `webkit2gtk`, не тащит Chromium |
| **tray-icon** | иконка и меню в трее | работает через `libappindicator` |

Размер релизного бинаря — **~5.5 МБ** (потяжелел после добавления `zbus` ради
single-instance — второй запуск не плодит новое окно, а будит уже открытое;
размер может немного гулять между сборками). Для сравнения: Electron-версия весила бы
100+ МБ, потому что тащит внутрь целый Chromium. Здесь браузер берётся из
системы (в Fedora это `webkit2gtk-4.1`), а не кладётся в комплект.

## Как собрать

Собирается **один раз**. Дальше запускается готовый файл.

> В примерах ниже `~/Projects/VOICEog` — папка, куда ты положил проект. У нас он
> лежит именно там; у тебя может быть другое место — подставь своё.

```bash
cd ~/Projects/VOICEog/window
cargo build --release
```

Готовый файл появится здесь:

```
~/Projects/VOICEog/window/target/release/voiceog-window
```

Первая сборка — долгая (5–15 минут): Rust качает и компилирует зависимости.
Повторные — секунды, если ничего не менял.

### Что должно стоять в системе для сборки

Проверено на этой машине (Fedora 44):

| Пакет | Зачем |
|---|---|
| `rust`, `cargo` | сам компилятор Rust |
| `webkit2gtk4.1-devel` | движок, который рисует морду |
| `gtk3-devel`, `glib2-devel`, `libsoup3-devel` | то, на чём стоит webkit |

Ставятся одной строкой:

```bash
sudo dnf install rust cargo webkit2gtk4.1-devel gtk3-devel glib2-devel libsoup3-devel
```

Для **работы** (не сборки) окну нужны уже другие пакеты: `webkit2gtk-4.1` и
`libappindicator-gtk3`. В Fedora они подтягиваются сами при установке
`gnome-shell-extension-appindicator`.

## Как запустить

```bash
~/Projects/VOICEog/scripts/run-window.sh
```

Скрипт делает всё за тебя и **безопасен при повторном запуске**:

1. Проверяет, отвечает ли сервер VOICEog на `http://127.0.0.1:7777/health`.
2. **Отвечает** — не трогает его (может, это systemd или ты сам запустил).
3. **Не отвечает** — поднимает сервер в фоне (с правильным `LD_LIBRARY_PATH`)
   и ждёт, пока тот проснётся и загрузит модель.
4. Открывает окно.
5. Ты закрыл окно — скрипт **гасит только тот сервер, который поднял сам**.
   Чужой сервер не трогает никогда. Иначе был бы цирк: открыл окно, закрыл —
   а у тебя погас сервер, которым пользуется что-то ещё.

Есть отдельная защита: если окно уже открыто, второй раз оно не откроется.
`VOICEOG_WINDOW_ALLOW_MULTI=1 scripts/run-window.sh` снимает **только**
`pgrep`-проверку самого лончера. Защиту в бинаре (`zbus`,
`window/src/single_instance.rs`) эта переменная не трогает: на живом сессионном
D-Bus второй бинарь всё равно уйдёт в Secondary, разбудит первое окно и выйдет —
второго окна не будет. Несколько окон реально открыть лишь там, где сессионного
D-Bus нет (тогда защита бинаря и так выключена) — вот там `ALLOW_MULTI`
действительно даёт второе окно.

### Как понять, что всё живо

```bash
curl -s http://127.0.0.1:7777/health
# {"ok":true,"model":"sherpa-onnx-nemo-parakeet-tdt-0.6b-v3-int8"}

pgrep -x voiceog-window      # должен показать номер процесса
ss -tlnp | grep 7777         # сервер слушает порт
```

## Автозапуск: окно само при входе в систему

### Способ 1 — .desktop (рекомендуется)

```bash
bash ~/Projects/VOICEog/scripts/install-window-autostart.sh
```

Скрипт кладёт файл `~/.config/autostart/voiceog-window.desktop`. При входе
система видит его и запускает `run-window.sh`, а тот поднимает сервер (если
надо) и открывает окно.

Почему так: файл в `~/.config/autostart` понимают **все** основные рабочие
столы — GNOME, KDE, XFCE и прочие, и на X11, и на Wayland. Ему не нужен
systemd. Снять: `bash scripts/install-window-autostart.sh --remove`.

> **Важно про конфликт.** Если у тебя уже стоит старый автозапуск
> (`~/.config/autostart/voiceog.desktop`, только сервер), то при входе два
> запуска кинутся поднимать сервер на один порт — один упадёт. Лучше оставить
> что-то одно. `run-window.sh` умеет и сервер поднять, поэтому старый снимаем:
> `bash scripts/install-autostart.sh --remove`.

### Способ 2 — systemd --user (заготовка)

Лежит готовый шаблон юнита — `voiceog-window.service` (рядом, в `docs/`).

В нём нет жёсткого `/home/...`: путь задан через `%h` — спецификатор systemd, который подставляет домашний каталог пользователя. Поэтому юнит ставится как есть на любую машину и любого юзера.

```bash
cp ~/Projects/VOICEog/docs/voiceog-window.service \
   ~/.config/systemd/user/voiceog-window.service
systemctl --user daemon-reload
systemctl --user enable --now voiceog-window
```

**Те самые env-грабли, из-за которых окно не появляется.** `systemd --user` —
это отдельный маленький мир, он **не наследует переменные твоего логин-сеанса
автоматически**. А окну, чтобы вообще возникнуть, нужно знать, куда рисоваться:

- на Wayland — переменная `WAYLAND_DISPLAY` (обычно `wayland-0`);
- на X11 — `DISPLAY` (обычно `:0`).

Если их нет — процесс стартует, но окна не будет: ему некуда подключаться.
Проверить, что реально видит systemd:

```bash
systemctl --user show-environment | grep -E 'WAYLAND_DISPLAY|DISPLAY'
```

На Fedora с GNOME эти переменные обычно уже импортированы (сессия сама их
прокидывает). Если пусто — раскомментируй строки `Environment=` в юните и
впиши свои значения (свои посмотреть: `echo "$WAYLAND_DISPLAY $DISPLAY"`).

Почему в `ExecStart` стоит `run-window.sh`, а не сам бинарь: скрипт гарантирует,
что сервер жив, и аккуратно гасит только свой.

## Трей и почему нужен перелогин

Иконка в трее — это отдельная история под GNOME.

**GNOME сам, из коробки, иконки трея не рисует.** Он принципиально убрал
системный трей. Чтобы иконки появились, нужно расширение
`gnome-shell-extension-appindicator` — оно умеет показывать программы, которые
кладут иконку по стандарту AppIndicator/KStatusNotifierItem (а `tray-icon`
делает именно так).

Оно уже стоит:

```bash
rpm -q gnome-shell-extension-appindicator
# gnome-shell-extension-appindicator-64-1.fc44.noarch
```

И его UUID прописан во включённых расширениях:

```bash
gsettings get org.gnome.shell enabled-extensions
# [..., 'appindicatorsupport@rgcjonas.gmail.com']
```

**А теперь главное — почему нужен logout/login.** GNOME Shell читает список
расширений **один раз при запуске**. Если расширение поставили и включили уже
после входа в систему, текущий Shell про него просто не знает. Убедиться можно
так:

```bash
gnome-extensions info appindicatorsupport@rgcjonas.gmail.com
# Расширение "…" не найдено        <-- так и есть, пока не перелогинился
```

Файлы расширения на месте, в настройках включено, а живой Shell его не видит.
На X11 можно было бы на ходу перезапустить Shell (Alt+F2 → `r`). На **Wayland
так нельзя** — Shell не умеет перезапускаться на лету. Значит — **выйти и войти
заново**. После этого иконка появится.

**Что будет, если не перелогиниться:** программа работает, окно открывается,
запись и распознавание в порядке — просто иконки в трее нет. `libappindicator`
полезет в устаревший запасной путь и будет сыпать в консоль предупреждения
`Gtk-CRITICAL … gtk_widget_get_scale_factor`. Это не смертельно, это симптом
«трей-хоста нет». Появится хост — предупреждения уйдут.

> Привычка: **поставил/включил расширение под GNOME на Wayland — сразу
> перелогинься.** Сэкономишь себе полчаса поисков «почему иконки нет».

Если трей или запуск всё равно не работает — см. [`troubleshooting.md`](troubleshooting.md);
про Windows — [`windows.md`](windows.md).

## Почему запись идёт через AudioWorklet (а не MediaRecorder)

Это был **главный баг** окна, и лечится он не в окне, а в морде.

### Как было

Морда писала звук старым добрым способом: `MediaRecorder` (штатный API браузера
«запиши мне поток с микрофона»). В обычном браузере он работает. В **WebKitGTK**
(движке, который использует `wry`) — **нет**.

### Что ломалось

`MediaRecorder` внутри WebKitGTK кодирует звук через GStreamer (`encodebin`), и
на этой сборке он отдаёт **пустой блоб** — ноль байт, хотя снаружи всё выглядит
нормально. Плюс `decodeAudioData` для формата webm/opus в WebKitGTK тоже врёт.

Получалась коварная штука: клиент «отрабатывал», ошибок не показывал, а звука в
записи **не было**. Сервер честно получал тишину и отвечал «тишина — ничего не
разобрал». Виноват был не сервер и не модель — виноват был способ записи.

### Как стало

Запись переписали **мимо кодировщика** — вообще без сжатия и без контейнеров от
браузера:

1. `getUserMedia` даёт сырой поток с микрофона.
2. **AudioWorklet** (отдельный `public/pcm-worklet.js`) прямо в аудиопотоке
   превращает звук в сырые целые числа **PCM s16le** и отдаёт кусками.
3. Страница склеивает куски и навешивает **44-байтный WAV-заголовок** — это уже
   полноценный .wav.
4. Готовый WAV уходит на `POST /transcribe`.

Декодирования в браузере нет вообще. Сервер сам читает частоту из WAV и
ресемплит, если она не 16 кГц (проверено 16 / 44.1 / 48 кГц). Резервный путь,
если AudioWorklet недоступен, — старый `createScriptProcessor`.

> Почему так правильно: мы перестали доверять браузерному кодировщику, который
> врёт, и берём звук в самом сыром виде. WAV — это просто «числа подряд плюс
> заголовок», тут ломаться нечему.

### Микрофон в вебвью

Отдельная мелочь, из-за которой кнопка сначала писала «the user denied
permission»: WebKitGTK по умолчанию **запрещает** микрофон. В коде окна
разрешение выдаётся **только** на микрофон (`PermissionKind::Microphone`), всё
остальное (камера, геолокация, буфер) — отказ. Навигацию окно пускает только
на адрес самой морды (по умолчанию `http://127.0.0.1:7777`, меняется
`VOICEOG_PORT`/`VOICEOG_URL`) — чтоб морда не уехала на чужой сайт.

## Почему `WEBKIT_DISABLE_DMABUF_RENDERER=1`

При запуске на Wayland WebKitGTK падал прямо на старте:

```
Gdk-Message: Error 71 … dispatching to Wayland display
```

Причина — **DMABUF-рендерер**. Это способ показывать картинку «напрямую» через
видеопамять, без лишнего копирования. Быстро — но на связке WebKitGTK + Wayland
(особенно с некоторыми драйверами) он сбоит, и окно не переживает старт.

Лечение: сказать WebKitGTK «не используй DMABUF, рисуй обычным путём».

```
WEBKIT_DISABLE_DMABUF_RENDERER=1
```

В коде окна эта переменная выставляется **самой первой строкой**, ещё **до**
инициализации GTK — позже уже поздно. `run-window.sh` выставляет её на всякий
случай повторно (если снаружи не задали иную). Это не «костыль от нас» — это
стандартный обходной путь для WebKitGTK под Wayland; платим за него чуть
меньшей плавностью отрисовки, а не работоспособностью.

## Пакеты: .rpm, .deb, AppImage

Упаковка: `.rpm`, `.deb` и AppImage собраны. AppImage бывает под двумя именами
(CI — `...-x86_64.AppImage`, локально под старую glibc — `...-x86_64-bookworm.AppImage`),
совместимость у обоих одна — glibc 2.35. Подробности ниже. Держи в голове два
разных места.

**Исходники упаковки** (то, из чего собирается) — в `window/packaging/`:

```
window/packaging/voiceog-window.desktop     — ярлык для меню приложений
window/packaging/icon-256.png               — иконка 256×256
window/packaging/appimage/build.sh          — рецепт сборки AppImage
```

**Готовые файлы** (то, что ставим) — в `window/target/` (сборный мусор, в git не едет):

```
window/target/debian/voiceog-window_*.deb          — для Debian/Ubuntu
window/target/generate-rpm/voiceog-window-*.rpm    — для Fedora/RHEL
window/target/appimage/voiceog-window-*.AppImage   — «один файл, любой Linux»
```

Пересобрать при желании:

```bash
cd ~/Projects/VOICEog/window
cargo build --release
cargo deb                          # -> target/debian/*.deb
cargo generate-rpm                 # -> target/generate-rpm/*.rpm
bash packaging/appimage/build.sh   # -> target/appimage/*.AppImage
```

Как ставить:

| Формат | Кому | Как |
|---|---|---|
| **.rpm** | Fedora, RHEL, openSUSE | `sudo dnf install ./voiceog-window-*.rpm` |
| **.deb** | Debian, Ubuntu, Mint | `sudo apt install ./voiceog-window_*.deb` |
| **.AppImage** | любой Linux | `chmod +x voiceog-window-*.AppImage && ./voiceog-window-*.AppImage` |

Разница по-человечески: **.rpm** и **.deb** — это «поставить в систему» (файл
кладётся в меню приложений, потом ставится/удаляется как обычная программа).
**AppImage** — это «один файл, ничего не ставит»: скачал, сделал исполняемым,
запустил. Удобно, чтобы попробовать, не трогая систему.

Локально сейчас лежит bookworm-вариант —
`voiceog-window-0.1.0-x86_64-bookworm.AppImage`:

- собран на Debian 12 (bookworm) скриптом `packaging/appimage/build-bookworm.sh`.
  Потолок `glibc 2.35`, поэтому заводится на Debian 12, Ubuntu 22.04+ и Fedora.
  ~90 МБ.

Суффикс `-bookworm` появляется только у локальной сборки: `build-bookworm.sh`
гоняет `build.sh` в контейнере `debian:bookworm` и на выходе приписывает суффикс.
CI зовёт `build.sh` напрямую на `ubuntu-22.04` (та же `glibc 2.35`) и отдаёт файл
**без** суффикса — `voiceog-window-0.1.0-x86_64.AppImage`. Для юзера разницы нет:
совместимость у обоих одинаковая, имена взаимозаменяемы. Хочешь собрать под
свежий дистр — `build.sh` на текущей системе, но там `glibc` свежее, и на старые
дистры такой образ не поедет.

> Эти пакеты ставят **только окно**. Сервер VOICEog — отдельный (Node), он
> ставится из исходников проекта. Пакет окна тянет за собой `webkit2gtk-4.1`,
> `gtk3` и `libappindicator-gtk3`, которые нужны ему для рисования морды.

## Автозапуск окна и сервер: как это связано

Держи в голове простую схему:

```
вход в систему
   └── ~/.config/autostart/voiceog-window.desktop
          └── scripts/run-window.sh
                 ├── сервер жив?  → не трогаем
                 ├── нет           → поднимаем (или ждём systemd voiceog.service)
                 └── открываем окно voiceog-window
```

Сервер может подниматься двумя путями: этим скриптом или юнитом
`voiceog.service` (systemd --user). Скрипт специально **сначала проверяет, не
поднимает ли сервер systemd**, и если да — просто ждёт. Так не бывает гонки «два
сервера на один порт».

## Ограничения, честно

- **Адрес морды настраивается.** Окно по умолчанию ходит на
  `127.0.0.1:7777`, но origin навигации считается от того же адреса:
  `VOICEOG_PORT`/`VOICEOG_URL` меняют и адрес, и разрешение вместе
  (`window/src/main.rs`, `with_navigation_handler`). Хардкода 7777 в белом
  списке нет — при смене порта морда грузится.
- **Одно окно.** Защита живёт в самом бинаре: через D-Bus (`zbus`) первый
  экземпляр занимает well-known имя, а второй не плодит новое окно, а поднимает
  уже открытое первое и выходит (`window/src/single_instance.rs`). Поверх этого
  `run-window.sh` ещё и сам не запускает второй пульт: перед стартом проверяет
  `pgrep -x voiceog-window` и, если окно уже открыто, просто выходит.
  `VOICEOG_WINDOW_ALLOW_MULTI` снимает только эту `pgrep`-проверку лончера и на
  сам бинарь не влияет: на живом сессионном D-Bus zbus-защита всё равно удержит
  одно окно. Несколько окон возможны лишь без сессионного D-Bus — там защита в
  бинаре отключается сама, и тогда `ALLOW_MULTI` пускает второе окно. Взаперти
  между двумя окнами переключения нет — пока так.
- **Трей после перелогина.** До первого logout/login иконки в трее не будет;
  программа при этом работает.
- **Только linux-x64 / linux-arm64.** Движок распознавания приходит готовыми
  бинарниками под эти архитектуры. На musl (Alpine) и riscv — сборка из
  исходников.

Если что-то из этого не работает — см. [`troubleshooting.md`](troubleshooting.md);
про Windows — [`windows.md`](windows.md).

