# Чек-лист: что проверить руками в окне VOICEog

Живая проверка, без автотестов. Идём по порядку, каждый пункт — «делаю →
ожидаю → если не так, что это значит». Проверяем на этой машине (Fedora 44,
GNOME на Wayland).

Перед стартом: окно должно быть собрано (`cd window && cargo build --release`),
иначе всё упрётся в «окно не собрано». Запуск — `scripts/run-window.sh`.

Если что-то из чек-листа не проходит — смотри [`troubleshooting.md`](troubleshooting.md);
про Windows — [`windows.md`](windows.md).

---

## 1. Трей (иконка-микрофон)

Трей — самая капризная часть, потому что GNOME сам иконки не рисует: их
показывает расширение `appindicator`.

**Делаю (по шагам):**
1. Проверить, что расширение стоит и включено:
   ```bash
   rpm -q gnome-shell-extension-appindicator
   gsettings get org.gnome.shell enabled-extensions
   ```
2. **Перелогиниться** (выйти из сеанса и войти заново). Не перезагрузка, а
   именно logout/login.
3. Запустить окно: `scripts/run-window.sh`.

**Ожидаю:**
- В трее (правый верхний угол, за «шторкой» — клик по часам/иконкам) висит
  **иконка-микрофон** цвета VOICEog.
- Правый клик по ней (или левый — меню открывается и так) → четыре пункта:
  **Показать / Скрыть**, **Перезагрузить**, **Открыть в браузере**, **Выход**.
- «Показать / Скрыть» и левый клик по иконке — окно прячется/появляется.
- «Перезагрузить» — морда в окне перезагружается.
- «Открыть в браузере» — морда открывается в обычном браузере.
- «Выход» — окно закрывается.
- **Крестик в окне не закрывает программу, а прячет в трей.** Проверка: жму
  крестик → окно исчезло, но процесс жив (`pgrep -x voiceog-window`), иконка в
  трее на месте, клик по «Показать» возвращает окно.

**Если не так:**
- **Иконки нет вообще.** Почти всегда — не перелогинился. Файлы на месте,
  `gsettings` показывает расширение, но живой GNOME Shell читает список
  расширений один раз при входе и про новое не знает. Проверка:
  `gnome-extensions info appindicatorsupport@rgcjonas.gmail.com` → «не найдено».
  Лечение — logout/login (на Wayland перезапустить Shell на ходу нельзя).
- **В консоли сыпется `Gtk-CRITICAL … gtk_widget_get_scale_factor`.** Это
  симптом «трей-хоста нет» — `libappindicator` ушёл в устаревший запасной путь.
  Программа работает, иконки просто нет. Тот же перелогин.
- **Крестик убил программу.** Тогда single-instance-защита не сработает (см.
  пункт 4) и окно будет подниматься заново. Пишем задачу.

## 2. Запись прямо в окне

**Делаю:**
1. В окне нажать большую кнопку **«НАЖМИ И ГОВОРИ»**.
2. Сказать в микрофон короткую фразу (например, «проверка раз два три»).
3. Нажать **«СТОП»**.

**Ожидаю:**
- После нажатия кнопка меняется на «СТОП», а статус под кнопкой становится
  **«слушаю…»**.
- После «СТОП» статус ненадолго **«распознаю…»**, затем — **«готово · N мс»**
  (N — реальное число, например 300–900 мс).
- В текстовом поле справа появляется распознанная фраза живым текстом.
- Повторная диктовка не стирает старое: новый текст **дописывается** снизу.

**Если не так:**
- **Статус «нет доступа к микрофону: …».** Вебвью не получил доступ. В коде окна
  микрофон разрешён (`PermissionKind::Microphone`), значит либо микрофон занят
  другой программой/выключен на уровне системы, либо сломался запрос разрешения.
  Глянуть логи сервера и системный звук.
- **Статус «тишина — ничего не разобрал».** Запись прошла, но звука в ней нет —
  либо молчали, либо писали слишком коротко (меньше ~0.15 с), либо микрофон
  отдаёт ноль. Важно: это **не** вина модели и **не** «сервер сломался» — раньше
  так врал `MediaRecorder` внутри WebKitGTK, теперь звук берётся сырым PCM и
  вранья быть не должно. Проверь микрофон и повтори фразу погромче/подольше.
- **Статус «ошибка: …».** Сервер не ответил на `/transcribe` либо вернул ошибку.
  Смотреть консоль сервера (пункт 7). Частая причина — сервер не поднят.

## 3. Хоткей (диктовка по клавишам в любое окно)

**Делаю:**
1. В окне, в блоке настроек, кликнуть в поле хоткея и нажать комбинацию, например
   `Ctrl+Alt+V`. Поле подскажет «нажми «Сохранить», чтобы применить».
2. Нажать **«Сохранить»**.
3. Проверить, что бейдж **«хоткей: активно (…)»** зелёный, а не красный.
4. Уйти в **другое** приложение (редактор, браузер, мессенджер), поставить курсор
   в поле ввода.
5. Нажать свою комбинацию → сказать фразу → нажать комбинацию ещё раз (или
   завершить диктовку по логике хоткея).
6. Дождаться, пока текст вставится.

**Ожидаю:**
- Запись стартует по хоткею даже когда окно VOICEog не в фокусе.
- Распознанный текст **сам вставляется** в то поле, где стоит курсор.
- Бейдж движков показывает, чем пишем и чем вставляем, например
  «пишу: parec · вставляю: wtype» с зелёным фоном.

**Если не так:**
- **Бейдж красный: «хоткей: не активен».**

  → сервер не смог захватить клавиатуру. Нужен доступ к `/dev/input`:
  `bash scripts/install-input-access.sh`, затем перелогин.
- **Бейдж «вставляю: НЕ готово».** Нет тула для вставки/Ctrl+V (`ydotool`,
  `dotool`, `wtype`, `xdotool`) или не настроен `/dev/input`. Текст тогда может
  распознаться и лечь в буфер, но сам не вставится.
- **Хоткей не срабатывает в другом окне.** Проверь, что это не комбинация,
  которую перехватывает система (Настройки → Клавиатура → Свои комбинации).
  Скрипт `scripts/setup-hotkey.sh` ставит глобальный биндинг GNOME на
  `voiceog toggle` (по умолчанию `Ctrl+Alt+V`) — это **другой** хоткей,
  он только дёргает «старт/стоп», а не вставляет текст сам.

## 4. Single-instance (второго окна быть не должно)

**Делаю:**
1. Убедиться, что окно уже открыто.
2. Во втором терминале запустить `scripts/run-window.sh` ещё раз.

**Ожидаю:**
- Второй терминал пишет **«окно уже открыто — второй пульт не поднимаю»** и
  завершается с кодом 0.
- Второго окна **нет**, второй иконки в трее **нет**.
- Если запустить сам бинарь напрямую
  (`window/target/release/voiceog-window`), второй экземпляр не создаёт окно, а
  **поднимает и фокусирует уже открытое окно первого** (через D-Bus) и молча
  выходит.

**Если не так:**
- **Открылось два окна / две иконки.** Сломалась защита. Проверь, что запускаешь
  именно `run-window.sh` (у него есть `pgrep`-проверка), и что не стоит
  `VOICEOG_WINDOW_ALLOW_MULTI=1` (она снимает только `pgrep`-проверку лончера;
  на живом D-Bus второе окно всё равно не поднимется — его удержит zbus-защита в
  бинаре).
- **Второй бинарь не поднял первое окно.** Значит D-Bus-мост (`zbus`) не сработал
  или окно первого зависло. Проверить `pgrep -x voiceog-window` и логи.

## 5. Другой порт

**Делаю:**
```bash
VOICEOG_PORT=7998 ./scripts/run-window.sh
```

**Ожидаю:**
- Сервер поднимается на порту 7998, окно грузит морду с
  `http://127.0.0.1:7998/` — **без правок кода**.
- Проверка живости: `curl -s http://127.0.0.1:7998/health` → `{"ok":true,…}`.
- Белый список навигации в окне считается от фактического адреса: порт 7777
  нигде не зашит, морда не уедет и не откажется грузиться.

**Если не так:**
- **Морда пустая / белая.** Значит окно ходит не туда, куда поднялся сервер, либо
  белый список считает origin неверно (тогда это баг, а не настройка).
- **Окно поднимается, но сервер на 7777.** Смотри, не активен ли
  `voiceog.service` (он всегда слушает 7777). На нестандартном порту скрипт
  специально поднимает сервер сам, юнит не трогает.

## 6. Автозапуск (окно само при входе)

**Делаю:**
1. Поставить автозапуск:
   ```bash
   bash scripts/install-window-autostart.sh
   ```
2. Проверить, что файл появился:
   `ls ~/.config/autostart/voiceog-window.desktop`.
3. **Перелогиниться.**
4. Ничего не запускать руками — ждать.

**Ожидаю:**
- При входе в систему окно VOICEog появляется **само**.
- Сервер при этом тоже поднимается (через `run-window.sh`), иконка в трее на месте.
- Если до этого стоял старый автозапуск только сервера
  (`~/.config/autostart/voiceog.desktop`), скрипт выведет **предупреждение** о
  возможной гонке за порт.

**Если не так:**
- **Окна нет.** Глянуть `~/.config/autostart/voiceog-window.desktop` — верен ли
  `Exec` (полный путь к `run-window.sh`). Проверить, что бинарь собран.
- **Два процесса дерутся за порт.** Значит остался старый автозапуск сервера.
  Снять его: `bash scripts/install-autostart.sh --remove`.
- **Окно стартует, но «пустое» на Wayland.** Возможно, автозапуску не хватает
  переменных окружения дисплея — но через `.desktop` они наследуются от сеанса,
  так что чаще дело в неактивном расширении трея (см. пункт 1).

Снять автозапуск: `bash scripts/install-window-autostart.sh --remove`.

## 7. Где смотреть, если что-то не так

- **Логи сервера:** `server.log` в корне проекта (если сервер поднят вручную или
  через автозапуск с логом). Если сервер поднял `run-window.sh` — он `exec`-ит
  `node src/server.mjs` и пишет прямо в консоль.
- **Запуск окна из терминала** — лучший способ увидеть правду: окно печатает
  предупреждения GTK/WebKit, а `run-window.sh` — что делает по шагам.
  ```bash
  ~/Projects/VOICEog/scripts/run-window.sh
  ```
  (в debug-сборке окно дополнительно печатает размер окна и прочую отладку).
- **Жив ли сервер:**
  ```bash
  curl -s http://127.0.0.1:7777/health
  pgrep -x voiceog-window          # номер процесса окна
  ss -tlnp | grep 7777              # слушает ли кто порт
  ```
- **Переменные дисплея для systemd-варианта автозапуска:**
  `systemctl --user show-environment | grep -E 'WAYLAND_DISPLAY|DISPLAY'`.
  Пусто — окну некуда рисоваться, окна не будет.
- **Расширение трея:**
  `gnome-extensions info appindicatorsupport@rgcjonas.gmail.com`.

Если зелёные пункты 1–6 — окно полностью живое: трей, запись, глобальный хоткей,
